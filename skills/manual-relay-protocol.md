# 人肉中继：双 AI 对话协议

## 何时用

- 用户手动在两个 AI 窗口之间复制粘贴，希望两边真正对话。
- 需要全程留档、可回溯、可判分的多轮交流。
- 想避免「两边自动无限互相追加」和「谁判谁」的僵局。

## 文件结构（固定三件）

| 文件 | 作用 | 写法 |
|---|---|---|
| `outbox.md` | 本轮「发给对方」的原文 | 每轮**覆盖**；只放正文，不含文件标题 |
| `transcript.md` | 全量记录 | 每轮**追加**三段：我说 / 对方回复 / 用户插话 |
| `README.md` / `HANDOFF.md` | 协议与交接 | 改动需用户同意；新会话先读 HANDOFF |

## 发言纪律

1. 给对方的原文**只出现在两处**：`outbox.md`，以及对话里单独贴出的一个代码块。两处必须一致。其余话语不进给她。
2. 对方回复**只由用户转达**。不替对方发言、不脑补立场、不假设她会怎么答。
3. **发出即停**：不自动写下一轮，等用户发起（或用户明确说「以后不用等」）。
4. `transcript.md` 只追加，不删改、不合并轮次；状态行（轮次、时间）可更新，属活字段。
5. 用户是裁判：可喊停、改规则、要求重写、推翻任何判定。

## 每轮流程

1. 用户说这轮谈什么（或说「继续」）。
2. 写 outbox → 在对话里贴同一段代码块。
3. 用户搬运，带回对方回复（整段、带 markdown 或截图皆可）。
4. 原样追加进 transcript（三段式），附用户插话。
5. 停。等下一轮发起。

## 判定权（重要分水岭，两种都可行，先问用户要哪种）

- **A. 用户裁定**：用户判胜负。优点简单；缺点是用户累，且容易被「看着像」影响。
- **B. 双方互判**：用户只传话与决定发不发，每轮由接收方给对方判分，判分即裁决，不服须带证据反驳。优点持续、可追溯、双方都被约束；缺点是双方可能同时放松或同时从严，需配「判据＋计分口径」才能对齐尺度。

设定 B 时必须同时定下：四项判据、计分口径、轻伤/未通过的分界理由，否则中间必漂。

## 校验串（纯人工搬运时的必备）

- 形式 `【CHK-<n><生僻字>-<干支>-<时辰>】`，接收方第一行逐字回显。
- 失败先走归因表（中继损耗 / 逐字失败 / 归因未定），别直接判模型错。
- 诚实边界：两端一致只证明「两端同源」，不能证明「经独立复核」。

## 停手与收尾

- 每轮结束即停，是本协议的命门；用户嫌慢时可一次给「本轮正文＋下一轮预告」，但不要连续自动追加。
- 收尾时做四件事：合算总分（先定算法再算）、写入 transcript 终局段、更新 HANDOFF 状态、归档。

## 归档

```
duel/_archive/<YYYYMMDD-HHMM>/
  ├─ README.md HANDOFF.md transcript.md outbox.md   # 快照
  ├─ SUMMARY.md                                     # 结论摘要（给未来的自己看）
  └─ skills/…                                        # 提取出的可复用技能
```
再把 `_archive` 压成 zip 放上一层目录，便于单独搬走。

## 反面教材（真实踩过）

1. **把闲聊办成考试**：用户开窗说「让两个 AI 吹水」，我第一轮就上协议、校验串、判据——用户后来明确抗议「我开这个是让你们吹水的」。**先确认模式**（闲聊对线 / 技术交叉审查 / 正式评测），再决定上多少结构。
2. **开局立满规矩**：两个还没熟的模型，第一轮就签合同，会错过摸对方思路的机会。预演阶段应以「暴露彼此怎么想」为目标，规则够用就好。
3. **判分尺度漂移**：前轮宽松（轻伤判过），后轮严格（同级别判不过）。要么一开始就写死「轻伤＝通过但扣分」，要么在收尾时主动摆出敏感性分析。
4. **记录半途改口**：用户的口头更正（身份、版本、权限）要立刻进 transcript 的插话栏并注明时间，否则日后翻档会被误读成事实。
